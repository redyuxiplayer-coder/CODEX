# 员工发货上报页面优化设计

## 目标

优化员工手机端发货上报页面，解决订单数量多时仅靠一个长下拉框难以核对的问题；同时要求员工填写真实发货日期和完整物流信息，使提交后的发货记录自动关联可供内部导出的快递记录。

本次包含三部分：

1. 发货日期可见、必填并可在未提交草稿中修改；
2. 订单按公司和款式/颜色筛选，同时支持订单号搜索；
3. 快递或货拉拉物流信息必填，包含包裹件数和总重量，并支持多个订单共用同一物流记录。

## 现状

- 员工通过 `/mobile/report` 创建包货草稿，再提交为正式发货记录；
- 页面把全部未归档正式订单放在一个原生下拉框中，订单较多时难以查找和核对；
- 草稿日期由隐藏字段固定为当天，员工看不到也不能修改；
- 页面只显示当天未提交草稿，过去日期草稿保存后会消失；
- 运单号为可选字段，只复制到发货记录快照，不会自动创建或关联 `WaybillRecord`；
- 草稿没有物流包裹件数和重量字段。

## 页面流程

### 1. 发货日期

- “新增包货草稿”顶部显示“发货日期”日期选择框；
- 字段必填、默认今天，浏览器端最大可选日期为今天；
- 允许选择今天或过去日期，不允许未来日期；
- 每张未提交草稿显示发货日期，并提供日期选择框供员工保存修改；
- “我的包货草稿”显示当前员工全部未提交草稿，不再限定为当天；
- 草稿仍按最近更新时间、创建时间倒序排列；
- 提交后员工不能在“我的上报”修改正式发货日期，修正仍由老板处理。

### 2. 订单筛选、搜索和核对

新建草稿的订单选择顺序为：

1. 选择公司；
2. 选择该公司下的款式/颜色组合；
3. 可选填写订单号搜索词；
4. 最终订单下拉框只显示同时满足筛选和搜索条件的订单。

筛选和订单号搜索可以同时使用。清空某一级筛选时，下游选项同步重置，避免保留已经不匹配的订单。

订单候选只包含当前有效、未归档的正式订单。每条候选固定显示：

`订单号｜下单日期｜颜色｜还差尺码数量`

示例：

`ZP-00028-CPLL｜2026-06-10｜红色｜还差 L98 / XL63`

如果所有尺码均不欠货，显示“已发完”，但只要订单尚未归档仍可显示，保持现有归档规则不变。

选中订单后继续显示该订单各尺码的客户 SKU、下单数量、已发数量、还差数量和超发数量。一次草稿仍只能对应一张正式订单。

订单筛选所需信息由现有正式订单候选数据提供，并增加每张订单的剩余尺码摘要。当前订单规模可在浏览器端完成筛选，无需新增独立搜索服务。

### 3. 物流信息

发货方式必选：

- 快递；
- 货拉拉。

两种方式都必须记录：

- 包裹件数：包裹、箱或包的数量，必须是大于 0 的整数；
- 总重量：单位 kg，允许小数，必须大于 0。

这里的包裹件数不是服装数量；服装数量仍由各尺码数量输入框记录。

#### 快递

- 真实运单号必填；
- 员工必须同时填写包裹件数和总重量；
- 多个订单属于同一票快递时，分别创建草稿并填写同一运单号；
- 相同运单号最终只对应一条 `WaybillRecord`，多个正式发货记录共同关联该记录；
- 同一运单号在公司、发货日期、包裹件数或重量上不一致时拒绝保存或提交，并提示员工核对。

#### 货拉拉

员工选择货拉拉后，再选择：

- 新建货拉拉车次；
- 已有货拉拉车次。

新建车次时：

- 系统生成唯一车次号，格式为 `货拉拉-YYYYMMDD-NNN`；
- 例如 `货拉拉-20260821-001`；
- `NNN` 使用新草稿数据库 ID 补足三位，超过三位时保留完整 ID，从而避免并发新建产生重复车次号；
- 员工填写该整车的包裹件数和总重量。

已有车次候选来自同公司、同日期的未提交/已提交草稿以及现有 `WaybillRecord`，因此第一张订单尚未提交时，后续草稿也能选择同一车次。选择后，系统带出车次号、件数和重量，员工不能为同一车次填写另一组数据。

同一车包含多个订单时，第一张订单新建车次，后续订单选择已有车次。每张订单分别生成正式发货记录，但都关联同一条 `WaybillRecord`，内部导出只出现一行，不重复累计整车重量或件数。

## 草稿和正式提交

### 保存草稿

日期、订单、发货方式、物流识别号、包裹件数、总重量和至少一条正数尺码数量都通过校验后，才允许保存新草稿或修改草稿。

快递草稿使用真实运单号作为物流识别号。新建货拉拉车次时，服务端生成车次号并写入草稿现有的 `waybill_no` 字段；选择已有车次时，草稿保存该车次号。

草稿修改日期或公司后，如果原物流记录不再与新日期或公司一致，必须重新选择物流信息，不允许静默沿用。

### 提交上报

提交草稿时，服务端再次执行全部日期、订单、物流和所有权校验，不能仅依赖保存草稿时的结果。

验证通过后：

1. 按物流识别号查询 `WaybillRecord`；
2. 不存在时，以草稿的公司、日期、识别号、件数和重量创建记录；
3. 已存在时，校验公司、日期、件数和重量完全一致后复用；
4. 生成 `ShipmentReport`，其 `ship_date` 使用草稿日期，`waybill_no` 保留识别号快照；
5. 设置 `ShipmentReport.waybill_id`，把正式发货记录关联到该物流记录；
6. 标记草稿已提交。

自动创建的 `WaybillRecord.courier`：快递保存为“快递”，货拉拉保存为“货拉拉”；`created_by` 保存提交员工 ID。老板后续可以在快递记录页把“快递”修正为中通、顺丰等具体公司。

上述校验和写入必须作为一个完整提交处理；任何冲突都不得留下半条正式发货或重复快递记录。

## 服务端校验

### 日期

1. 去除首尾空格；
2. 空白时提示“请填写发货日期”；
3. 不能按 `YYYY-MM-DD` 解析时提示“发货日期格式不正确”；
4. 晚于服务器当前日期时提示“发货日期不能晚于今天”。

### 订单

- 订单必须存在、有效且未归档；
- 所有尺码行必须属于同一张所选订单；
- 页面筛选不替代现有服务端订单绑定校验。

### 物流

- 发货方式不是“快递”或“货拉拉”时提示“请选择发货方式”；
- 快递运单号为空时提示“请填写运单号”；
- 包裹件数不是正整数时提示“请填写正确的发货件数”；
- 总重量不是正数时提示“请填写正确的总重量”；
- 物流识别号与既有草稿或快递记录的数据冲突时，提示具体冲突字段并拒绝操作；
- 已有货拉拉车次与当前公司或日期不一致时拒绝选择。

浏览器端的 `required`、`min`、`step` 和日期 `max` 用于减少误操作，服务端校验负责防止绕过页面直接提交。

## 权限

- 员工只能创建自己的草稿；
- 员工只能修改、删除和提交自己的未提交草稿；
- 已提交草稿不能修改；
- 物流车次可以被同公司、同日期的多个订单引用，但这不放宽草稿所有权；
- 老板保留现有快递记录编辑能力。

## 数据结构和迁移

`PackingDraft` 新增三个字段：

- `shipping_method`：字符串，保存 `courier` 或 `huolala`；
- `package_count`：整数，保存包裹件数；
- `weight_kg`：浮点数，保存总重量。

继续使用现有 `PackingDraft.waybill_no` 保存真实运单号或货拉拉车次号。

`ShipmentReport` 和 `WaybillRecord` 不新增字段。正式提交后，重量和包裹件数进入 `WaybillRecord`，发货记录通过现有 `waybill_id` 关联。

需要提供 PostgreSQL 幂等迁移，并同步更新应用现有的结构补齐逻辑。新增列使用空字符串或 0 作为旧数据默认值；既有未提交草稿必须补齐物流信息后才能再次保存或提交。

## 测试

自动测试覆盖：

### 日期

- 页面显示必填日期框，默认今天且最大日期为今天；
- 过去日期草稿可以创建、显示和修改；
- 空白、格式错误和未来日期均被拒绝，原数据不变；
- 提交后的 `ShipmentReport.ship_date` 与草稿一致。

### 订单选择

- 候选仅包含有效、未归档订单；
- 公司、款式/颜色和订单号搜索可以单独及组合筛选；
- 候选文字包含订单号、下单日期、颜色和剩余尺码摘要；
- 选中订单后仍按订单行显示尺码余额；
- 服务端继续拒绝跨订单尺码行。

### 物流

- 未选择方式、快递缺运单号、件数无效、重量无效均不能保存；
- 快递草稿完整填写后可保存和提交；
- 相同运单号的多个订单复用一条 `WaybillRecord`；
- 相同运单号数据不一致时拒绝且不产生半条记录；
- 新建货拉拉车次生成唯一编号；
- 同公司同日期的后续订单可选择已有车次；
- 不同公司或日期不能复用货拉拉车次；
- 多个货拉拉订单提交后只产生一条 `WaybillRecord`；
- 自动生成的快递记录包含正确日期、件数和重量，并出现在内部导出“快递记录”页；
- 客户版导出结构保持不变。

### 权限和回归

- 员工不能修改、删除或提交他人的草稿；
- 员工不能修改已提交草稿；
- 已提交记录的员工更新表单不提供发货日期或物流主数据修改入口；
- 现有订单归档、数量校验、照片、备注和装箱单功能继续工作。

## 实现边界

- 本次只优化员工手机端发货上报、包货草稿服务、自动快递记录关联及相关测试；
- 不修改订单编号、SPU、客户 SKU 或条形码规则；
- 不修改客户版导出结构；
- 不新增日历工作区、批量改日期、路线跟踪、司机信息或运费结算；
- 不自动猜测两个不同运单号属于同一票物流；
- 不按“公司 + 日期”自动合并货拉拉，以免同一天两车被误合并。
