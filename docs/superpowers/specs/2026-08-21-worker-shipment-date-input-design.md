# 员工发货上报填写发货日期设计

## 目标

员工在手机端发货上报时可以明确填写实际发货日期，不再由隐藏字段固定写成当天。日期必填、默认今天，可选择今天或过去日期，不允许未来日期。

## 现状

员工通过 `/mobile/report` 创建包货草稿，再提交为正式发货记录。现有页面使用隐藏字段把当天写入 `PackingDraft.pack_date`，员工看不到也不能修改；提交草稿时，系统把 `pack_date` 复制到 `ShipmentReport.ship_date`。

页面当前只查询当天的未提交草稿。如果仅允许员工选择过去日期而不调整查询范围，过去日期草稿保存后会从页面消失。

## 页面设计

### 新建包货草稿

- 把隐藏的 `pack_date` 改成可见的“发货日期”日期选择框；
- 字段必填；
- 默认值为今天；
- 浏览器端最大可选日期为今天；
- 订单、尺码、运单号和备注流程保持不变。

### 未提交草稿

- “我的包货草稿”显示当前员工的全部未提交草稿，不再限定 `pack_date == today`；
- 每张草稿在醒目位置显示发货日期；
- 草稿修改表单增加“发货日期”日期选择框，预填草稿当前日期；
- 员工保存修改时可以同时修改日期、尺码数量、运单号和备注；
- 草稿仍按最近更新时间、创建时间倒序显示。

### 已提交记录

- 点击“确认无误，提交上报”后，继续把草稿的 `pack_date` 写入正式发货记录的 `ship_date`；
- 员工不能在“我的上报”中修改已提交记录的发货日期；
- 已提交日期如需修正，仍由老板在现有管理流程中处理。

## 服务端规则

新建草稿和修改草稿共用同一套发货日期校验：

1. 去除首尾空格；
2. 空白时拒绝并提示“请填写发货日期”；
3. 不能按 `YYYY-MM-DD` 解析时拒绝并提示“发货日期格式不正确”；
4. 晚于服务器当前日期时拒绝并提示“发货日期不能晚于今天”；
5. 今天或过去日期允许保存。

浏览器的 `required` 和 `max` 只用于减少误操作，服务端校验负责防止绕过页面直接提交。

修改草稿继续执行现有所有权检查：只有草稿创建员工本人可以修改。日期校验不会放宽订单归档、订单行绑定、数量或权限规则。

## 数据与组件边界

- 不新增数据库字段，不需要数据库迁移；
- 继续使用 `PackingDraft.pack_date` 保存未提交草稿的发货日期；
- 继续使用 `ShipmentReport.ship_date` 保存提交后的正式发货日期；
- 日期校验放在包货草稿服务中，供新建和修改路径复用；
- 手机页面负责显示字段，FastAPI 路由接收表单值，服务层负责最终校验和保存。

## 错误处理

日期不合规时不保存任何草稿变更，并返回明确的中文错误。现有路由可继续把服务层 `ValueError` 转为 HTTP 400，保持项目当前错误处理方式。

如果员工选择过去日期创建草稿，保存后仍返回发货上报页，并能在全部未提交草稿列表中看到该草稿及其日期。

## 测试

自动测试覆盖：

- 发货上报页包含可见、必填的发货日期框，默认今天且最大日期为今天；
- 新建过去日期草稿成功；
- 新建空日期、格式错误日期和未来日期均被拒绝；
- 当前员工的过去日期未提交草稿仍显示在发货上报页；
- 员工可以修改自己未提交草稿的日期；
- 修改为空日期、格式错误日期或未来日期时拒绝且原数据不变；
- 员工不能通过修改接口更改他人的草稿；
- 提交过去日期草稿后，生成的 `ShipmentReport.ship_date` 与草稿日期一致；
- 已提交记录的员工更新表单不出现发货日期编辑字段。

## 实现边界

- 只改员工手机端包货草稿及其服务和测试；
- 不改老板端已提交记录修改流程；
- 不改客户版或内部版导出结构；
- 不改快递记录、订单编号、SPU、客户 SKU 或条形码功能；
- 不新增日期筛选工作区、日历视图或批量改日期功能。
