# 正式订单归档设计

## 目标

为正式订单增加独立归档能力。已发完的订单由老板手动归档后，不再出现在员工订单列表和新建发货选择中；老板仍可查询、恢复，历史发货、快递信息和导出保持完整。

首次上线后，批量归档当时所有符合完成条件的正式订单；后续由老板逐单手动操作。

## 已确认规则

- 归档采用独立表，不修改 `sales_orders.status`，也不停用 `order_lines`。
- 只有管理员可以归档和恢复。
- 仅当订单所有尺码的剩余数量都小于或等于 0 时允许归档。
- 超发不阻止归档；只要不存在仍需发货的尺码即可。
- 归档只影响员工订单列表、新建发货选择和新发货绑定。
- 历史发货、照片、快递单号、订单详情、内部版导出和客户版导出全部保留。
- 需要补发或返工时，管理员先恢复订单。
- 管理端正式订单页提供“进行中 / 已归档 / 全部”筛选。

## 数据模型

新增 `sales_order_archives` 表，每次归档建立一条记录：

- `id`：主键。
- `order_id`：正式订单 ID，外键指向 `sales_orders.id`，建立索引。
- `archived_by`：归档管理员 ID。
- `archived_at`：归档时间。
- `restored_by`：恢复管理员 ID，可空。
- `restored_at`：恢复时间，可空并建立索引。

一条 `restored_at IS NULL` 的记录表示订单当前处于归档状态。恢复时填写该记录的恢复人和恢复时间；再次归档时新增记录，因此归档和恢复历史不会丢失。

服务层在事务中检查同一订单不存在另一条未恢复记录，防止重复归档。由于项目同时支持 SQLite 测试和 PostgreSQL 生产环境，不引入仅 PostgreSQL 支持的部分唯一索引。

数据库迁移必须幂等：建表、索引和外键在重复执行时不会破坏已有数据。应用启动的兼容性迁移负责新环境初始化；生产部署仍按照既有流程，由 PostgreSQL 管理员显式执行迁移并核验表结构。

## 完成条件判定

归档服务使用现有订单余额规则计算指定正式订单的每个尺码：

`剩余 = 下单数量 - 有效发货 + 退回 - 调整 - 关闭`

必须满足：

- 订单存在至少一条有效明细；
- 每条明细对应的最终剩余数量均 `<= 0`；
- 不存在仍需发货的尺码。

有效发货仍只包含 `auto_approved` 和 `approved_after_edit`，驳回记录不计入。超发产生负数剩余，允许归档。

若条件不满足，接口返回明确错误，例如“L 码还需 98 件，不能归档”，不写入任何归档记录。

## 服务与接口

新增独立归档服务，职责包括：

- 查询订单是否归档；
- 批量查询归档订单 ID，避免列表逐行查询；
- 校验完成条件并归档；
- 恢复当前归档；
- 返回归档历史。

新增管理员接口：

- `POST /api/v1/sales-orders/{order_id}/archive`
- `POST /api/v1/sales-orders/{order_id}/restore`

两个接口均要求管理员登录。归档和恢复写入 `operation_logs`，记录订单号、操作类型和操作者。

正式订单列表接口增加 `archive_status=active|archived|all`，默认 `active`。订单详情返回：

- `is_archived`
- 当前归档信息
- 归档/恢复历史
- 是否满足归档条件
- 不能归档时仍欠货的尺码和数量

## 员工端隐藏与防绕过

不能只在页面上隐藏，服务端必须同时限制：

1. `/mobile/orders` 过滤已归档正式订单的余额行。
2. 新建发货页的公司、款式和订单候选项不从归档订单产生。
3. 自动匹配订单行时跳过已归档订单。
4. 员工或管理员提交新发货时，如果显式选择了已归档订单，服务端拒绝并提示先恢复订单。
5. 历史发货记录仍显示原订单号、下单时间、快递和照片，不删除或改写绑定关系。

管理员余额页、订单详情和导出继续使用完整订单数据，不因归档过滤。

## 管理端界面

### 正式订单列表

- 增加“进行中 / 已归档 / 全部”筛选，默认“进行中”。
- 增加状态列，显示“进行中”或“已归档”。
- 已归档订单仍可进入详情。

### 正式订单详情

- 未归档且已发完：显示“归档订单”按钮。
- 未归档但仍欠货：按钮禁用，并显示仍欠货尺码和数量。
- 已归档：显示归档人、归档时间和“恢复订单”按钮。
- 页面保留尺码、客户 SKU、订单信息和历史数据入口。

归档与恢复操作均二次确认，成功后刷新订单详情和列表状态。

## 首次批量归档

提供一次性管理脚本，复用正式归档服务，不直接拼接状态 SQL。流程为：

1. 只读预览所有正式订单及逐尺码余额。
2. 输出拟归档订单数和订单号清单。
3. 备份生产 PostgreSQL。
4. 显式使用 `--apply` 执行归档。
5. 每张订单产生独立归档记录和操作日志。
6. 重新查询验证：拟归档清单全部已归档；仍欠货订单均保持进行中；员工候选列表不再出现归档订单。

该脚本只在本次上线执行一次，之后由管理员界面手动归档。

## 导出与历史兼容

- 内部版和客户版导出不排除已归档订单。
- “订单”“下单时间”、客户 SKU、发货明细和快递单号继续按原规则输出。
- 云端同步到本地 SQLite 时同步归档表，确保本地审计结果与生产一致。
- 删除订单仍需单独权限和流程；归档不是删除。

## 测试与验收

### 自动化测试

- 数据表与幂等迁移测试。
- 未发完订单归档失败，并返回欠货尺码。
- 正好发完订单归档成功。
- 超发订单归档成功。
- 重复归档失败且不产生重复开放记录。
- 恢复成功，并保留历史记录。
- 员工订单列表和新建发货候选项隐藏已归档订单。
- 直接提交已归档订单的新发货被服务端拒绝。
- 管理端筛选正确。
- 内部版、客户版导出仍包含已归档订单。
- 归档前后的历史发货、快递和照片关联不变。

### 生产验收

- 完整测试通过后再部署。
- 部署前备份数据库和照片目录。
- 健康检查、管理端首页和静态资源返回 200。
- 首次批量归档先预览再执行。
- 抽查至少一张正好发完、一张超发、一张仍欠货订单。
- 用员工账号确认归档订单不再出现在订单页和发货选择中。
- 实际生成内部版和客户版工作簿，确认归档订单仍保留在历史及汇总中。

## 不在本次范围

- 自动归档。
- 按日期定时归档。
- 员工自行恢复订单。
- 删除历史发货或订单。
- 因退回返工自动恢复；管理员按需手动恢复。
