# 正式订单号、内部 SPU 与客户 SKU 设计

日期：2026-08-09

## 目标

建立正式订单主表，使订单、员工发货上报和照片之间具有明确、稳定的归属关系；同时建立跨公司共用的内部 SPU，并把客户 SKU 作为订单尺码行上的可选快照字段。

本阶段不改造条形码系统。

## 核心业务规则

### 订单边界

一张订单必须且只能对应：

- 一个公司
- 一个内部 SPU
- 一个产品
- 一个款式
- 一个颜色；无颜色时允许为空
- 多个尺码行

不同款式或不同颜色必须分别建立订单。系统在新增和编辑订单时强制校验，不能在同一订单中混入其他公司、SPU、款式或颜色。

### 发货边界

员工一次发货上报必须先选择一个订单，并且只能提交该订单下的尺码数量。一次上报、该次上传的照片和生成的发货记录都只能归属于这一个订单。

如果同时发出两个订单，员工必须分别上报。

## 数据模型

### 公司

在现有公司数据上增加：

- `code`：公司代码，由用户手工维护，全系统唯一，例如 `YXF`、`ZP`、`ART`
- `next_order_sequence`：该公司下一次订单序号，或采用等价的事务安全计数机制

公司代码只参与新订单号生成。订单号生成后，即使公司代码以后修改，旧订单号也保持不变。

### 内部 SPU

新增内部 SPU 主数据。SPU 是供应商自己的基础款式标识，跨公司共用。

主要字段：

- SPU 编码：全系统唯一，可手工填写；留空时由系统生成
- 产品名称
- 款式名称
- 备注
- 启用状态

同一个基础款式卖给不同公司时，共用同一个内部 SPU。

### 正式订单

新增订单主表，主要字段：

- 系统订单号：全系统唯一、生成后不可变
- 客户订单号：可选，由用户手工填写
- 公司
- 该公司内部订单序号
- 内部 SPU
- 产品名称快照
- 款式名称快照
- 颜色名称：可空
- 颜色编码：可空
- 下单日期
- 交期
- 备注
- 状态
- 创建时间和更新时间

产品、款式和颜色保存订单快照，避免以后修改 SPU 主数据时改变历史订单含义。

### 订单尺码行

现有订单行归入正式订单，主要字段：

- 订单 ID
- 尺码
- 下单数量
- 客户 SKU：可空文本
- 交期或行备注（如业务仍需要）

客户 SKU 不建立独立映射表，不自动带出历史值，也不自动生成。客户本次提供就填写，没有就留空。每张订单保存自己的客户 SKU 快照，修改新订单不影响旧订单。

### 发货记录

发货主记录增加必填订单 ID。发货尺码行仍绑定具体订单尺码行，以保留数量抵扣和追溯能力。

发货照片通过发货记录确定唯一订单。已有的快递关联继续保留，不改变快递记录的核心结构。

## 系统订单号

格式：

`公司代码-公司订单序号-SPU编码[-颜色编码]`

示例：

- 有颜色：`YXF-00001-JS-RED`
- 无颜色：`YXF-00002-JS`

规则：

- 中间序号按公司分别从 `00001` 开始递增
- 序号代表该公司的第几次下单
- 公司代码、SPU 编码和颜色编码生成订单号前必须符合允许的编码格式
- 无颜色时省略颜色段，数据库颜色字段保持空白
- 订单号生成必须使用数据库事务或唯一约束，避免并发创建重复序号
- 系统订单号生成后不可编辑；订单内容需要更正时不重算旧订单号
- 客户订单号与系统订单号分开保存，不参与系统唯一编号

## 页面与流程

### 公司管理

增加公司代码维护。没有公司代码的公司不能新建正式订单。

### SPU 管理

提供 SPU 列表、新增、编辑、停用和查询。新增订单时从已启用 SPU 中选择。

### 新增订单

流程：

1. 选择公司
2. 选择内部 SPU
3. 自动带出产品和款式
4. 填写颜色名称和颜色编码；无颜色时留空
5. 填写下单日期、客户订单号、交期和备注
6. 添加多个尺码、数量和可选客户 SKU
7. 保存时生成该公司的下一个系统订单号

系统必须检查同一订单只有一个 SPU、款式和颜色，并防止同公司序号重复。

### 员工发货上报

员工先选择订单号，页面只显示该订单的产品、款式、颜色和尺码行。提交时后端再次验证所有订单行都属于所选订单，不能仅依赖前端限制。

### 发货明细

每条发货记录显示：

- 系统订单号
- 客户订单号（有则显示）
- 内部 SPU
- 产品、款式和颜色
- 员工、发货日期、上报时间
- 尺码数量、照片、状态和快递信息

订单号可点击进入订单详情。由于一次发货只允许一个订单，照片的订单归属不会产生歧义。

### 订单详情

显示订单头、各尺码数量和客户 SKU，并汇总该订单关联的所有发货、照片、退回、核销和关闭流水。

## 历史数据迁移

迁移分为可自动处理和需要用户确认两组。

### 可自动处理

对有明确下单日期的历史订单：

1. 按现有公司、产品、款式、原批次和下单日期识别订单分组
2. 生成迁移预览，不直接改生产数据
3. 用户确认公司代码和 SPU 归属
4. 每家公司按下单日期、创建时间、原记录 ID 稳定排序
5. 从 `00001` 开始生成公司内序号和系统订单号
6. 把原订单行归入订单主表
7. 根据现有 `shipment_lines.order_line_id` 回填发货主记录的订单 ID

迁移时不得根据款式名称猜测颜色。颜色不明确时进入待确认清单。

### 必须逐条确认

以下历史记录不能自动编号：

- 缺少下单日期
- 无法唯一判断订单分组
- 同一历史分组疑似包含多个款式或颜色
- 发货行跨越多个候选订单
- 缺少公司代码或 SPU 归属

系统输出待确认清单，由用户逐条补充下单日期、公司代码、SPU、颜色或分组决定。确认后才正式编号，不使用虚构日期或猜测值。

### 安全要求

- 修改生产数据前备份 PostgreSQL 数据库和照片目录
- 先在本地云端快照上演练迁移
- 迁移脚本支持预览、执行和迁移后审计
- 迁移后核对订单行数量、发货数量、照片数量、快递关联和余额
- 任何无法唯一回填订单的发货记录必须停止迁移并进入待确认清单

## API 与校验

新增或调整的接口应覆盖：

- 公司代码管理
- SPU 管理
- 正式订单增删改查
- 按订单上报发货
- 发货明细返回订单信息
- 历史迁移预览与待确认清单

后端必须执行以下校验：

- 公司代码、SPU 编码和系统订单号唯一
- 公司内订单序号唯一
- 订单只包含一个 SPU、产品、款式和颜色
- 发货主记录只绑定一个订单
- 发货尺码行必须属于发货主记录所绑定的订单
- 客户 SKU 可空，不参与唯一性校验

## 测试与验收

至少覆盖：

- 不同公司分别从 `00001` 开始编号
- 有颜色和无颜色订单号格式
- 手工与自动 SPU 编码
- 客户订单号可空
- 客户 SKU 可空且不自动沿用上一订单
- 一个订单可包含多个尺码
- 同一订单不能混入不同款式或颜色
- 一次发货不能跨订单
- 发货明细和照片能追溯到唯一订单
- 历史有日期订单的稳定排序和编号
- 历史无日期订单进入待确认清单
- 迁移前后订单数量、发货数量、照片和余额一致

## 本阶段不包含

- 条形码生成、打印或扫码规则
- 客户 SKU 主数据或自动映射
- 库存管理
- 采购和供应商管理
- 根据名称自动猜测颜色或 SPU
